# JavaScript Integrity

## Threat model

The browser executes JavaScript served by the Mindful Money origin. If an
attacker compromises the server (or the deploy pipeline), they can replace
the crypto code with a version that exfiltrates keys or plaintext.

## Defenses (layered)

### 1. Subresource Integrity (SRI)

All `<script>` tags in `index.html` include `integrity="sha384-..."` attributes.
The browser will refuse to execute a script whose hash doesn't match.

**Limitation:** SRI on same-origin scripts does not stop a fully compromised
origin. An attacker who controls the server can modify both `index.html`
(which contains the hashes) and the JS files. SRI primarily protects against:
- Accidental modification during deploy
- CDN or proxy tampering (if HTML and JS take different paths)
- Serves as an audit signal (unexpected hash changes are visible in git)

### 2. Integrity manifest

`static/integrity-manifest.json` contains SHA-384 (SRI) and SHA-256 hashes
for all crypto-relevant JavaScript files. Generated by:

```bash
python3 scripts/generate_integrity.py
```

Verify without modifying:

```bash
python3 scripts/generate_integrity.py --check
```

### 3. Deploy-time verification (CI)

The deploy workflow's smoke tests fetch the served JS files and compare
their SHA-256 hashes to the manifest from the deployed git commit. If they
don't match, the deploy is marked as failed.

This catches:
- Stale deployments (old JS served with new version tag)
- Accidental file corruption during build
- (Partial) server compromise that modifies JS but not the CI pipeline

### 4. Out-of-band verification (user)

Users can independently verify the served JS:

```bash
# Fetch the manifest from the repo (trusted channel)
curl -s https://raw.githubusercontent.com/PaulinoTech1/Mindful-Money/main/static/integrity-manifest.json

# Fetch served JS and compare hashes
curl -s https://mindful-money-k23ukkh5cq-uc.a.run.app/static/app.js | sha256sum
```

If the hashes don't match, do not enter your passphrase.

## What is NOT covered

- **Full origin compromise:** If the attacker controls both the server AND
  the CI pipeline (or the git repo), all bets are off. This is why we
  recommend out-of-band verification for high-value targets.
- **Browser compromise:** Malicious extensions, devtools, or a compromised
  browser can intercept keys regardless of JS integrity.
- **First-load trust:** The very first page load requires trusting the
  origin. There is no way around this for a web app (unlike a locally
  installed app with signed binaries).

## Future work

- **Signed manifest:** Sign the manifest with an offline key; publish the
  signature via a separate channel (e.g., GitHub release attestations).
  The browser extension or a standalone verifier checks the signature.
- **Binary transparency:** Publish JS hashes to an append-only log
  (like Certificate Transparency) so silent replacement is detectable.
- **Browser extension:** A minimal extension that verifies JS hashes
  against the signed manifest before allowing passphrase entry.

## Regenerating after JS changes

Any change to `static/app.js`, `static/simplefin-client.js`, or vendor
files requires regenerating the manifest and SRI attributes:

```bash
python3 scripts/generate_integrity.py
git add static/integrity-manifest.json static/index.html
git commit -m "Update JS integrity hashes"
```

CI will fail if the manifest is out of date (add a check step).
